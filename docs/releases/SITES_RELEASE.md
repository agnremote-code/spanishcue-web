# SPANISHCUE Sites release controller

## Authority and transport

Canonical repository: agnremote-code/spanishcue-web. Site: appgprj_6a83ba10b0c481919060fc089d581233. Production origin: https://spanishcue.com. The single GitHub merge-event automation owns Sites lifecycle actions through native Sites tools. GitHub Actions performs CI and auto-merge; it cannot use the short-lived Sites source credential as a deployment API key. Do not invent HTTP endpoints or store Sites credentials in GitHub secrets.

State lives in state.json on branch automation/sites-release-state. It is not deployed source. Every update must create a commit whose parent is the EXACT state-branch HEAD read for that operation, then update_ref with force=false. Competing children cannot both fast-forward: the losing controller must reread and must not proceed. Never use update_file as a lock, force-update, delete or time-expire this branch.

## Release steps

1. Treat the event as a wake-up. Read state.json first; enabled must be true. A disabled bootstrap leaves production unchanged. Read the actual PR, main and Sites state. Require merged=true, base=main and same repository. Ignore non-main merges. If main advanced, process the newest actual merged main after its own CI succeeds, never the stale event SHA.
2. Require the corresponding CI + Auto Merge verify job, fresh-candidate verification and Post-merge health check to pass. Wait for the workflow to finish and automation/merge-lock to disappear. Reject failed, cancelled, unknown or missing checks. Source rollback commits also require their own verified evidence.
3. Fetch exact current main and the last healthy source into an isolated checkout. Confirm .openai/hosting.json project ID. Run release-policy.mjs classify BASE_SHA MAIN_SHA. Any exit 42 requires MIGRATION_RELEASE.md; do not publish. Check migration/config/infrastructure changes even if a PR label says safe. Initial v161 uses the recorded canonicalSha alias only after its migration-sensitive files were verified identical to deployed c49bd604aef109324f0bb7181182603322598e11.
4. Read state branch HEAD and state.json. If busy, do not deploy; wait for this owner to finish and reread. Never steal the lock. Use release-policy.mjs transition with acquire, a unique owner ID and candidate SHA. Persist that JSON by create_tree/create_commit(parent=read HEAD)/update_ref(force=false). Reread and verify both commit SHA and owner. The transition records previous healthy version/deployment/SHA BEFORE any release. If acquisition loses a race, discard its build decision and reread.
5. Wait for automation/merge-lock to disappear, then reread GitHub main and Sites versions/deployment. The CI merger checks release state before and after acquiring its merge lock, so releases block new merges. If main differs from candidate, cancel the lock (deploymentStarted=false) and restart from current main. If live source/environment/audience drifted from the recorded baseline or a deployment is already running, stop; never deploy over unknown state.
6. Run preflight production smoke. Build, validate and package the exact clean detached merged SHA following Sites skills. Use native source credentials only in per-command Git headers; never expose them. Push only that already merged SHA to the Site's configured source branch, without force. A non-fast-forward is a blocker, not permission to synthesize a different deployment SHA.
7. Immediately before save/deploy, recheck lock ownership, main SHA, successful CI and no pending Sites deployment. Save the exact merged SHA plus matching archive through native Sites. Persist candidate version ID to busy state before deploy. Deploy that saved version and persist deployment ID. If a response is lost, reconcile the version's deployment status before retrying; never start a duplicate deployment.
8. Poll deployment to a terminal state. Run node scripts/production-smoke.mjs against the custom production domain, then query recent Worker error logs and correlate only current smoke request times/routes. Required checks: homepage, login, genuine 404, free lesson, account redirect, PRO redirect, private audio denial, students API denial, Firebase session and Resend verification invalid-token rejection. These requests neither send email nor mutate accounts/data. A malformed/unauthenticated endpoint check does not establish email delivery; unchanged v161 delivery tests are preserved in CI.
9. On deployment or critical smoke/runtime failure, immediately redeploy state.previous.versionId with native Sites tools, then poll and rerun the SAME smoke suite. Never revert D1, modify environment secrets, or apply SQL. Only ordinary releases with unchanged migration-sensitive files reach this step. Record failed SHA and restored deployment ID with transition restored(smokePassed=true). If recovery fails or deployment status remains unknown, retain busy state, halt subsequent releases and report the exact incident. Do not unlock or claim success.
10. On success, transition healthy(smokePassed=true) with exact SHA, saved version ID, version number and deployment ID. Persist using the same non-force child-commit update. This advances healthy, appends the previous release to history and unlocks. After rollback, record failedSha so the same failed main is not automatically redeployed. A later fixed merge may be considered.
11. Before ending, reread main. If a newer merged SHA arrived while waiting, process it through the same gates. Report only deployed SHA/version/deployment, smoke, rollback if any, and blockers. Do not send Slack/email messages.

## Limits and recovery

GitHub webhook delivery and the automation runner determine start latency; this is not a synchronous GitHub-hosted deployment job. A crashed or interrupted owner deliberately leaves a busy lock, preserving its previous healthy version. Recovery must first reconcile Sites live/pending deployment and state ownership; it must never expire a lock based only on elapsed time. If native tools are unavailable, leave production unchanged and report the blocker.

The controller restores the last healthy saved Worker; it does not guarantee the hosting provider can complete an outage-time rollback. Do not claim a live rollback was tested based solely on policy unit tests.
